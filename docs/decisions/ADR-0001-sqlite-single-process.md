# ADR-0001: SQLite в одном процессе панели

- **Статус:** accepted
- **Дата:** 2026-11-10
- **Связь:** FR-3.15.1–3.15.3, раздел 7 ТЗ (границы)

## Контекст
Панель хранит пользователей, серверы, подключения, учёт трафика. Требования: целостность
учёта (fail-closed), идемпотентные операции, просто развёртывание (Docker volume), бэкап
копированием файла. Допустима ли клиент-серверная СУБД (Postgres)?

## Решение
Локальный SQLite (`panel.db`, путь `DB_FILE`), режим WAL, транзакции с `synchronous=FULL`
для критичных операций, запись — через единственный writer под `asyncio.Lock`
(`app/db/database.py`). **Панель — всегда один процесс**; горизонтальное масштабирование
не поддерживается (ТЗ §7.1, §7.5).

## Альтернативы
- **PostgreSQL** — отвергнуто: усложняет развёртывание и бэкапы; объёмы данных малы
  (единицы тысяч peers); `aiosqlite` покрывает нагрузку.
- **Несколько воркеров uvicorn** — отвергнуто: in-process блокировки и процессно-локальная
  CAPTCHA не разделяются между процессами; конкурентная запись в SQLite деградирует.

## Последствия
- Бэкап = снапшот файла (+ WAL-checkpoint); restore = атомарная замена файла (FR-3.11.1).
- Миграции упрощаются (встроенный мигратор `schema_version`).
- При необходимости роста — вынос в Postgres потребует отдельного ADR и мигратора данных.
- Контроллер запуска должен гарантирoвать единственный процесс (без `--workers > 1`).
